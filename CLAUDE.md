# CLAUDE.md — sport-app

> Index principal du monorepo. Sert de point d'entrée à Claude (et à un humain qui découvre le repo) : pointe vers les bonnes docs selon ce que tu cherches.

## En une phrase

Application sportive de tracking d'entraînement (séances de salle, programmation, progression hebdo, suivi par muscle), avec **fonctionnalités bonus** (chrono/timer, notifs, routines/tâches récurrentes), conçue pour devenir un compagnon "vie quotidienne" — extension future prévue : **nutrition (calories + macros)**.

## Architecture monorepo

| Dossier | Rôle | Stack |
|---|---|---|
| [`serveur/`](serveur/) | API backend + persistance + push temps-réel + sert le SPA web à `/` | FastAPI · Python 3.14 · SQLAlchemy 2 (async) · asyncpg · PostgreSQL 18 · Alembic · WebSockets |
| [`appli-android/`](appli-android/) | Application mobile (client) + app montre (module `:wear`, Galaxy Watch) | Kotlin · Jetpack Compose · Hilt · Room · Retrofit · OkHttp · Wear Compose · Health Services · Wearable Data Layer |
| [`appli-web/`](appli-web/) | Client web (SPA jumeau Android, offline-first), servi par FastAPI same-origin sur la Pi | Angular 22 (zoneless) · TypeScript · Dexie · echarts |

Le serveur tourne **en prod sur une Raspberry Pi** (`<public-dns>`, HTTPS via Caddy) et **en dev sur PC Windows** (`<pc-lan-ip>:8000`). L'app Android possède 2 build variants (`debug` → PC, `release` → Pi) qui injectent l'URL via `BuildConfig`.

## Quick reference (pour ne pas re-fouiller)

### Endpoints / IPs / domaines
- **Préfixe global** : tous les endpoints applicatifs sous `/api/v1/` (T3.2). Utility hors préfixe : `/healthz`, `/secure-docs`, `/token-helper`, `/webhook/deploy`.
- **PC dev** : `http://<pc-lan-ip>:8000/api/v1/` (HTTP, LAN local)
- **Pi prod** : `https://<pi-fqdn>/api/v1/` (Tailscale-only depuis 2026-05-21 via `tailscale serve` ; cert géré par Tailscale ; LAN local `<pi-lan-ip>` toujours OK depuis le tailnet). Public `<public-dns>` + Caddy : **dormants** (NAT/PAT Livebox coupé).
- **WebSocket** : `/api/v1/ws?access_token=...&client_id=...`
- **Doc API** : `/secure-docs` (Swagger custom, `/docs` désactivé) — login via `/token-helper`
- **Auth** : `POST /api/v1/token` (form-urlencoded `username`/`password`) → JWT access (HS256, 30 min) + refresh token long-lived (V8.2)
- **Webhook deploy** : `https://<pi-fqdn>:8443/webhook/deploy` (Tailscale Funnel, HMAC GitHub)

### Comptes / secrets
- **PC** : Postgres `fittracker:fittracker` / DB `fittracker` / `.env` local (gitignored), JWT secret réel
- **Pi** : secrets rotés V1.2 le 2026-05-11. Password Postgres alphanum 32 chars + `JWT_SECRET_KEY` hex 64 chars dans `/home/william/Applications/sport-app/serveur/.env` (`chmod 600`). Anciens `change-me` invalidés ; tous JWT précédents invalides → re-login requis pour clients qui n'avaient pas refait l'opération.
- **Users de seed** (créés par `fill_database.py`) : `will/<password>`, `bob/<password>`, etc.

### Commandes les plus utiles (PC)

## Conventions / consignes pour Claude

1. **Pas de modifications spéculatives** — l'utilisateur travaille en mode "état des lieux" puis "améliorations ciblées". Ne refactore pas sans demander.
2. **Toujours lire `DEV_GUIDE.md` au démarrage** — c'est la mémoire de setup que l'utilisateur a maintenue à jour.
3. **Langue** : documentation et discussions en **français**. Le code reste en anglais (Kotlin/Python identifiers existants).
4. **Ne JAMAIS lancer `python reset_db.py`** sans confirmation explicite : c'est destructif (drop toutes les tables). Le script demande déjà un prompt interactif (`reset` à taper), mais ne l'invoquer jamais en autonomie. Pour un setup safe (création des tables manquantes uniquement), utiliser `python setup_db.py` (idempotent).
5. **Avant de toucher au schéma DB**, lire `docs/DATABASES.md` (étape 4) — il y a des subtilités : Room `version=6` sans `Migration` définie (= crash si on bump sans plan), Alembic à moitié utilisé en parallèle de `Base.metadata.create_all`.
6. **Triggers SQL = realtime** : toute nouvelle table qui doit pousser des updates aux clients via WebSocket a besoin d'un fichier `<table>_trigger.sql` listé dans `app/triggers_loader.py:PER_TABLE_FRAGMENTS` (source unique partagée par `setup_db.py` / `reset_db.py` / `fill_database.py` + Alembic, cf. V3.3).
7. **Build Android** : si on modifie `BuildConfig` ou les URLs, faire **Clean Project + Rebuild** (cache Gradle).
8. **Politique de sécurité (validée 2026-05-03)** :
   - Aucun endpoint public — JWT obligatoire partout (y compris reads sur entités globales).
   - **Cascade ownership** sur les entités imbriquées : un set appartient à un workout d'un user, donc une op sur le set valide la chaîne jusqu'à User.
   - **Rôle admin** pour modifier les entités globales (equipment, training_cycle templates, etc.) : `User.is_admin` + `Depends(require_admin)` sur les writes Type C.
   - `user_id` jamais lu du payload client — toujours via `Depends(get_current_user_id)`.
9. **Politique d'uniformité des modules** — les CRUDs/routers/schemas/syncables/DAOs/APIs d'un même type doivent partager un squelette identique. Divergences acceptables seulement si fonctionnellement nécessaires. Squelette canonique CRUD défini dans [docs/SERVEUR.md §2B-1](docs/SERVEUR.md), squelette DAO dans [docs/APPLI_ANDROID.md §3D §2](docs/APPLI_ANDROID.md). **Précision 2026-05-04** : les fonctions du squelette canonique sont à **conserver dans tous les modules même si pas utilisées aujourd'hui** (au cas où elles servent plus tard). "Jamais appelée" n'est PAS un critère pour supprimer une fonction du squelette. Mais les **doublons stricts** (deux fonctions qui font exactement la même requête sur la même table) restent à dédupliquer.
10. **Politique des defaults DB (validée 2026-05-05)** — un `default` (Python ou `server_default` SQL) sur un modèle SQLAlchemy n'est légitime que si la valeur reflète une **sémantique métier majoritaire** (cas naturel par défaut). Exemples validés : `exercise_muscles.coefficient = 1.0` (= muscle ciblé en priorité, à 100%), `actual_workout_exercises.phase = "TRAINING"` (= exercice d'entraînement classique, vs WARMUP/POST_TRAINING qui sont des cas particuliers), `actual_workout_sets.is_dropset = False` (= set normal, ~95% des cas), `actual_workout_sets.status = "NOT_STARTED"` (= set créé pas encore commencé, F2c-1 2026-05-06). **Pas de default si la valeur est arbitraire** : `set_order` (position positionnelle, doit être explicite). `nullable=False + default=X` ne masque pas un `null` explicite — Postgres raise `IntegrityError` si on passe `null` ; le default ne kick que sur **omission** de la colonne dans l'INSERT.
11. **Politique UPPER_CASE pour les valeurs d'états (cross-stack, alignement complet 2026-05-06)** — toute valeur de type "état" (`status`, `phase`, `priority`, etc.) doit être en `UPPER_CASE` (e.g. `"NOT_STARTED"`, `"TRAINING"`, `"HIGH"`) cohérent **côté serveur** (Postgres + Pydantic) **et côté Android** (Room + Kotlin). ✅ Vague F2c-1 a aligné le dernier état lowercase résiduel (`actual_workout_sets.status = "in_progress"` → `"NOT_STARTED"` partout, migration Alembic `38449dc119b5`). Tout nouvel état doit suivre cette convention dès l'ajout.
12. **Politique des données orphelines (validée 2026-05-05)** — toute donnée user-scoped en base **qui n'a pas de `user_id` récupérable** (ex. au moment d'une migration qui ajoute une colonne `user_id`, ou lors d'un backfill) est par défaut **assignée à `user_id = 1`** (compte admin `will`, base de tests). Décision pragmatique pour la dev : ces orphelins sont presque toujours de la donnée test. Si production : changer cette politique avant la mise en service publique.
13. **Cohérence scripts de seed/fill ↔ modèles (validée 2026-05-05)** — à chaque modification de schéma (ajout de colonne, contrainte, default), **vérifier `app/seed_database.py` et `app/fill_database.py`** (et tout autre script de population) pour s'assurer qu'ils restent valides : ils doivent fournir explicitement les nouveaux champs obligatoires, respecter les nouvelles contraintes, et utiliser les valeurs métier attendues. À ajouter à la checklist mentale avant tout commit qui touche `app/models/`.
15. **Politique reload triggers post-rename (validée 2026-05-06, F7-fix)** — toute migration Alembic qui RENAME COLUMN sur une col **référencée par un fragment trigger SQL** (cf. `app/db_triggers/<table>_trigger.sql`) doit être suivie d'un reload de `notify_row_change()` via `from app.triggers_loader import compose_function_sql; op.execute(compose_function_sql())`. **Sinon** : le 1er UPDATE/INSERT sur la table renommée crashe en 500 avec `UndefinedColumnError: rec."<oldname>"` parce que la fonction PG en mémoire référence encore l'ancien nom. La migration F7-2 (`f72_reload_fn`) sert d'exemple. Idem si on **supprime** une col, change son type, ou ajoute/retire une col mentionnée dans un fragment.
14. **Politique de traçabilité des changements DB (validée 2026-05-06, F6-6 ; renforcée 2026-05-10)** — **🔴 OBLIGATOIRE** : toute modification structurelle de la base (ajout/suppression de table, ajout/suppression/renommage de colonne, changement de type/contrainte/default, ajout/suppression d'index, ajout/suppression de FK) **DOIT** être répercutée dans `app/diagram.dbml` **dans le même commit**. Pas de "je le ferai plus tard". Le DBML est le visuel de référence du projet — il doit toujours refléter l'état effectif des modèles SQLAlchemy. **Sources de vérité** :
    - **`app/models/*.py`** = état effectif Postgres (lu par Alembic `target_metadata = Base.metadata`).
    - **`app/diagram.dbml`** = visuel projet (mis à jour synchrone avec les modèles SQLAlchemy, jamais en retard).
    - **`docs/DATABASES.md`** = audit cross-check Postgres/Pydantic/Room (à régénérer quand le schéma bouge significativement).
    - **`docs/SERVEUR.md` §3 archétypes** = inventaire Type A/B/C des entités (à mettre à jour quand un type change, cf. V5.7 + F1d).
    - **`CLAUDE.md` historique de session** = chronologie des décisions (entrée par vague terminée).
    Convention : DBML = visuel synchrone, modèles SQLAlchemy = effectif. Quand on touche à un modèle, on touche au DBML dans le même commit. Pour les changements Room côté Android : KSP régénère automatiquement `appli-android/app/schemas/<N>.json` au build, à committer comme source de l'effectif Room.
16. **Politique Alembic vs `Base.metadata.create_all` (validée 2026-05-06, F8-Q3)** — `Base.metadata.create_all` n'est autorisé **que** dans les scripts de **bootstrap/reset/seed** : `setup_db.py` (idempotent, `checkfirst=True`, F9-Q5), `reset_db.py` (destructif avec confirm prompt, F9-Q5) et `app/fill_database.py` (re-seeding test, `checkfirst=True`). Toutes les **migrations incrémentales de schéma** passent par **Alembic** (`target_metadata = Base.metadata` branché V3.4 → `alembic revision --autogenerate -m "..."` disponible). En pratique : si tu modifies un modèle SQLAlchemy, tu **génères une migration Alembic** ; tu ne comptes jamais sur `create_all` pour propager le changement (il ne le fait que sur les tables manquantes, ne touche jamais aux schémas existants). La Pi prod n'exécute **JAMAIS** `setup_db.py` / `reset_db.py` / `fill_database.py` (les 3 lancent du `create_all` et/ou du `drop_all`). Le déploiement Pi (`deploy.sh`) applique uniquement `alembic upgrade head` + reload triggers (cf. politique 15). **Source de vérité du schéma effectif Postgres** = la chaîne `alembic upgrade head` depuis le baseline. Pas de bascule "tout-Alembic" (qui demanderait un baseline reconstruit) parce que l'hybride documenté marche aujourd'hui — gain marginal vs risque non négligeable sur la Pi prod.
17. **Politique de nommage cross-stack (validée 2026-05-07, T4.1)** — toute colonne qui apparaît dans un schéma Pydantic ou un payload WS doit être en **snake_case** côté serveur (Postgres + SQLAlchemy + Pydantic Python attr) avec son alias `camelCase` côté wire JSON (`Field(..., alias="camelCase")` + `model_config = {"populate_by_name": True}`). Côté Android : la propriété Kotlin reste `camelCase` (convention Kotlin) avec `@ColumnInfo(name="snake_case")` pour la colonne Room (cohérence DB). **Exception acceptée** : les colonnes Room **local-only** qui ne traversent jamais le wire (flags de sync : `synced`, `pendingDeletion`) peuvent rester en convention Kotlin (camelCase) sans `@ColumnInfo(name=...)`. Justification : aucun gain fonctionnel à les renommer (le code Kotlin n'utilise jamais le nom de colonne directement, juste les propriétés), et une migration Room pour rename touche les 22 tables → risque > bénéfice cosmétique. Audit T4.1 (2026-05-07) confirme : 67/68 colonnes en snake_case, seul `pendingDeletion` reste en camelCase et c'est OK (local-only).
18. **Politique i18n EN/FR obligatoire pour tout UI Android (validée 2026-05-12)** — 🔴 **OBLIGATOIRE** : tout élément textuel ajouté ou modifié dans l'UI Android (Compose) DOIT être ajouté dans `appli-android/app/src/main/res/values/strings.xml` (EN canonique) ET dans `appli-android/app/src/main/res/values-fr/strings.xml` (traduction FR) **dans le même commit**. Jamais de string hardcodée dans le code Kotlin Compose. Convention : utiliser `stringResource(R.string.xxx)` au lieu de `text = "..."`. Préfixes par écran (`home_*`, `session_*`, `stats_*`, `drawer_*`, `auth_*`, etc.) ou `common_*` pour les boutons réutilisés. **Cas spéciaux** :
   - Codes wire UPPER_CASE (MALE/FEMALE/OTHER, WARMUP/TRAINING/POST_TRAINING, DONE/NOT_STARTED, Monday/Tuesday/Sunday, Chest/Back/etc.) **NE SONT PAS** traduits côté stockage (politique 11). Display via helpers `localizedDayOfWeek` / `localizedZone` (cf. `utils/LocaleHelper.kt`) ou via `stringResource` inline avec mapping local.
   - Noms user-typed (workout names, exercise names custom) restent tels quels — ne JAMAIS traduire.
   - "Rest Day" filler PlannedWorkout : stockage EN canonique en DB, display via helper `localizedDayOfWeek("Rest Day")` (déjà géré).
   - Messages snackbar dans les ViewModels : injecter `@ApplicationContext context: Context` via Hilt et utiliser `context.getString(R.string.xxx)` car pas d'accès à `stringResource` hors Composable.
   - Notifications système (NotificationCenter) : pareil, `context.getString(R.string.xxx)`.
   **Pattern live switching** : la locale est observée globalement dans `MainActivity.setContent` via `OnboardingRepository.preferences` → un `CompositionLocalProvider` override `LocalContext` (wrappé dans `ContextWrapper(activity)` pour préserver Hilt) + `LocalConfiguration` avec la locale choisie. Tout `stringResource()` recompose automatiquement au tap dans Settings/onboarding. Pas besoin de `AppCompatDelegate.setApplicationLocales` (qui crashait sur ComponentActivity). **Tâche checklist mentale avant tout commit qui touche un fichier `.kt` UI** :
   1. Tous les nouveaux strings sont-ils dans `values/strings.xml` ?
   2. Et dans `values-fr/strings.xml` (traduction FR) ?
   3. Le code utilise `stringResource(R.string.xxx)` au lieu de littéraux ?
   4. Si codes wire enum (status, phase) : helper de mapping en place ?
19. **Politique de maintenance du diagramme d'architecture (validée 2026-05-27)** — 🔴 **OBLIGATOIRE** : [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) est un **document vivant** qui doit refléter l'état réel de la stack en permanence. Dès qu'un changement d'architecture est détecté (nouvelle entité majeure ajoutée, nouveau service, refonte sync layer, changement réseau Tailscale/Caddy, nouveau flow auth, nouveau build variant, nouveau host de déploiement, changement de stack technologique), Claude DOIT mettre à jour le ou les diagrammes Mermaid concernés **dans le même commit que la modification technique**, **sans attendre que l'utilisateur le demande**. Le diagramme §0 "Overview synthétique" est la vue de référence en haut du fichier — les §1-§7 détaillent chaque facette. Bandeau explicite en tête du fichier rappelle cette règle. Cohérent avec politique 14 (DBML synchro modèles) appliquée au niveau architectural.
